# 中文提示模板库

基于用户提供的 Codex-Engineering-Prompt-Playbook.md（2026-09-30）简化。原文件是参考材料，下面的代码块供复制到未来任务使用，不在整理时执行。

填法：替换【】即可；不知道的文件或命令写“不知道，请从项目中确认”。先选择“只调查”或“调查并实施”，再按需加技术补充。

## 一、理解与定位

### 1. 理解代码链路（只读）
适合接手陌生模块、梳理消息发送与接收流程。填写业务链路和模块。
```text
帮我理解【业务链路】，本轮只读，不修改代码。
从实际实现追踪 UI、状态管理、Service、SDK/API、缓存到 UI 更新；说明核心文件和方法、数据流、状态归属、异步边界及错误处理。
先给完整调用链和最值得阅读的文件，再列出有证据的风险。区分源码显示、文档说法和推断，不能只根据文件名总结。
```

### 2. Bug 调查（只读）
适合原因不明、需要先看证据的问题。填写现象、期望和触发条件。
```text
调查【问题现象】；期望行为是【正确行为】，已知触发条件是【条件/不知道】。
本轮只调查，不修改代码。
追踪相关执行路径、状态和数据变化；结合代码、日志或复现区分已确认事实、候选原因和待验证项。
给出最可能原因及证据、最小复现或验证办法、最小修复建议。证据不足时说明缺什么，不先加补丁掩盖症状。
```

### 3. 性能调查（先测量）
适合卡顿、慢请求、资源占用异常。填写现象和可量化目标。
```text
调查【性能现象】，目标是【耗时/帧率/资源目标，不知道可留空】。
本轮先定位和测量，不修改代码。优先使用项目已有 profiling 或 benchmark 工具。
找出关键路径、重复工作和主要瓶颈；分别给出测量证据、测量限制和最小优化实验。
不要凭感觉增加缓存。后续优化需在相同条件下比较前后指标，并说明内存、复杂度和行为变化。
```

## 二、实施与演进

### 4. 小改动
适合文案、明确的小型 UI/API 修改。填写改动和期望结果。
```text
完成【具体改动】，期望结果是【可观察行为】。
沿用现有实现方式，只改本任务需要的内容，避免无关重构。
完成后做适合这次改动的检查，告诉我修改位置、实际验证结果和未验证部分。
```

### 5. 新功能
适合边界明确的功能。填写用户操作和完成标准。
```text
实现【功能】。用户通过【操作】触发，应该看到【结果】。
范围是【模块/业务边界】，完成标准是【可验收条件】。
先阅读最相近的现有功能，说明可复用的组件、状态管理和数据层方案，再完成最小一致实现。
不扩散需求，不为局部功能创建第二套架构；涉及鉴权、权限或输入校验时说明实际风险。
运行相关测试和适用的静态检查，检查最终 diff，报告已验证行为和剩余风险。
```

### 6. Bug 调查并修复
适合用户已授权闭环处理。填写现象、期望和回归重点。
```text
调查并修复【问题】，期望行为是【正确行为】。
先找出真实执行路径并用代码、日志或复现验证原因。证据充分后继续实施最小修复，不改无关行为；证据不足时说明阻塞和下一步。
为关键故障补充能抓住该问题的回归验证，运行相关测试和适用检查，确认【回归重点】正常。
最后报告原因及证据、修改内容、实际运行的验证和未解决项。不要只以症状暂时消失判断完成。
```

### 7. 重构迁移（先试点）
适合范围较大的结构调整。填写目标和本轮试点范围。
```text
目标是【重构/迁移目标】，保持【外部行为或 public API】不变。
先盘点涉及模块、共享状态、依赖、副作用、生命周期和测试，按实际风险提出迁移顺序。
本轮只迁移【试点模块；未指定时选一个低风险代表模块】，验证行为后总结可复用做法和差异。
不同时重构无关架构，不直接扩大到全项目；报告试点结果、风险和下一批建议。
```

## 三、评估与质量

### 8. 架构评估（只读）
适合方案取舍。填写当前痛点和拟议方案。
```text
评估【方案】能否解决【实际痛点】，本轮不实施。
先调查当前职责、依赖、数据流和状态归属，证明现有问题，不默认我的方案正确。
比较最小演进、较大调整和维持现状：收益、迁移成本、复杂度、风险及适用边界。
指出关键假设和更简单的替代办法，给出推荐方案及最小可验证实验。
```

### 9. 测试设计
适合确定高价值验证；默认本轮先分析。
```text
分析【模块】最值得测试的用户行为，本轮先给测试方案，不写代码。
优先看状态变化、异步顺序、错误恢复和当前真实风险，按影响排序。
说明每个测试能抓住什么回归、如何观察结果，以及现有覆盖的缺口。
避免为覆盖率增加无意义测试，不测试私有实现细节。若后续授权写测试，只实现最高价值场景。
```

### 10. Code Review（只读）
适合当前 diff 或明确 PR。填写评审对象。
```text
Review【当前 diff/PR/提交】，本轮不修改代码。
结合调用方、相关状态和测试寻找真实可触发的问题，不只看 diff 表面。
每项发现给出位置、触发条件、实际影响、证据和最小修复建议，并按实际严重度排序。
不报告纯格式偏好或没有执行路径的理论风险。没发现重要问题就直说，并说明验证盲区。
```

## 四、验证与交付

### 11. 最终验收
适合已实施任务收口。填写原目标、标准和允许修复的范围。
```text
按原始目标【目标】和完成标准【条件】检查最终交付，本轮不新增功能。
运行相关测试、静态检查及适用的 build/typecheck；检查最终 diff、关键业务路径和范围外行为。
在已授权范围内修复本次修改造成的问题并重新验证；不覆盖用户已有改动。
报告：满足的条件、修改文件、实际验证命令及结果、未验证项、剩余风险和下一步。
测试通过、CI 通过、构建可安装和真机业务验收分别报告，不能互相替代。
```

### 12. 三段式追问
适合明确分阶段推进；三段是独立发送的提示。
```text
第一段：先只读调查【目标链路】，给出真实行为、状态归属、证据和待验证项，本轮不修改。
```
```text
第二段：基于前面的调查，在【范围】内实施最小正确修改，完成标准是【条件】。保持无关行为不变。
```
```text
第三段：按【完成标准】验证实现，在已授权范围内修复问题并重验，给出实际结果和剩余风险。
```

## 按需技术补充

只挑相关项附在模板后，不要全量套用。

- Flutter：检查相关 BuildContext/mounted、异步间隙、StreamSubscription/Timer dispose、Provider 生命周期及 rebuild 范围；使用项目已有 analyze/test 命令，不无条件运行依赖安装或代码生成。
- iOS/Swift：检查相关 MainActor/actor isolation、Task 取消、引用归属、observer/subscription 释放及前后台生命周期。
- Web：检查相关 stale closure、请求取消、重复请求、缓存失效、事件清理及 SSR/CSR 边界。
- 移动端业务验收：写明系统、设备、版本、业务操作和可观察结果；实际运行后才报告通过。

### IM 重复消息调查示例（只读）
```text
调查聊天消息偶发重复：本地 optimistic message 显示后，收到 server acknowledgement 偶尔出现两条；期望只保留一条逻辑消息。本轮只调查，不修改。
追踪插入消息的所有相关入口，检查 clientId/messageId 映射、消息确认、缓存、历史合并、重连和分页。
用实际代码和可获得日志区分重复到达与重复插入，给出复现办法、根因证据或待验证项及最小修复建议。
不要未经验证直接增加全局 Set 去重；修复阶段需验证确认、重连、分页和排序行为。
```
